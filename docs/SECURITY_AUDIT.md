## Методология

Аудит в режиме full-scan: `govulncheck ./...`, `gosec -quiet ./...`, grep-развёртка по классическим паттернам инъекций (`exec.Command`, `os.Open`/`os.ReadFile`, `net/http`, `database/sql`, `text/template`/`html/template`, `unsafe.`, `crypto/md5`/`sha1`/`rand`, `base64`, `tls.`, `os.Getenv`, конкатенация SQL), STRIDE-модель угроз на границах доверия (вход в `SubmitTask`, `ExecutorRegistry.Register`, `TenantProvider.List`), DREAD-скоринг находок, построчное прослеживание потоков данных через `pool.go`/`manager.go` для многотенантной изоляции и конкурентной безопасности. Находка №1 воспроизведена эмпирически отдельным тестом (не только через чтение кода).

## Findings

### 1. Задачи, ожидающие в очереди тенанта, теряют `Task.Complete` при удалении тенанта ✅ исправлено

**Категория:** concurrency-safety / resource-leak · **Severity:** средняя (DREAD ≈ 4.4 — Damage: средний, Reproducibility: низкая-средняя при обычной нагрузке, Exploitability: не требует атакующего ввода, Affected users: потенциально любой тенант, Discoverability: низкая до появления зависших горутин в проде)

`refreshTenants` при удалении тенанта только считает задачи, оставшиеся в буфере `taskQueue`, для отладочного лога — но не сливает их и не вызывает `Complete`:

```go
// manager.go, refreshTenants — ветка удаления тенанта
dropped := len(state.taskQueue)
state.cancel()
delete(w.tenants, id)
```

Параллельно `dispatch` выходит из цикла сразу при отмене контекста, не дочитывая буфер:

```go
// manager.go, dispatch
select {
case <-genCtx.Done():
    return
case task = <-state.taskQueue:
}
```

Если в `taskQueue` в момент отмены остаётся необработанная задача, `select` в Go недетерминированно выбирает один из готовых кейсов — задача может быть просто отброшена вместе с горутиной `dispatch`, и `task.Complete` для неё **никогда не вызывается**.

Это противоречит документированному контракту пакета: докстринг `Task.Complete` описывает вызов «ровно один раз ... включая остановку диспетчера», а sentinel-ошибка `ErrDispatcherStopped` (`errors.go`) прямо описывает этот сценарий («диспетчер тенанта остановился до захвата слота конкурентности для задачи») — но фактически используется только для одной задачи, на которой `dispatch` был заблокирован в `sem.Acquire` в момент отмены; остальные задачи в буфере эту обработку не проходят.

**Подтверждено эмпирически:** тенант с `WorkerLimit: 1`, одна задача выполняется (блокирует единственный слот), ещё две задачи поставлены следом (буферизуются, `dispatch` ещё не успел их прочитать) → тенант удаляется через `refreshTenants` во время выполнения первой задачи. Результат: задача A (в работе) и задача B (та, на которой `dispatch` блокировался в `sem.Acquire`) корректно получают `Complete(ErrDispatcherStopped)`; задача C, оставшаяся непрочитанной в буфере, `Complete` не получает вовсе.

**Практическое влияние:** вызывающий код, который блокируется в ожидании `Complete` (распространённый паттерн, используемый и в собственном тестовом наборе пакета — `done := make(chan error, 1)` + `Complete: func(err error) { done <- err }`), может зависнуть навсегда, если его задача проиграла эту гонку при удалении тенанта под нагрузкой с частой сменой состава тенантов. Утечка горутин/ресурсов, а не проблема безопасности памяти или инъекций — DoS-подобное следствие обычной работы системы, не требующее злонамеренного ввода.

**Исправление:** перед удалением тенанта `refreshTenants` теперь сливает `taskQueue` через новый метод `drainTaskQueue` и вызывает `Complete(ErrDispatcherStopped)` для каждой оставшейся задачи (`manager.go`):

```go
state.cancel()

dropped := w.drainTaskQueue(state)
delete(w.tenants, id)
```

```go
// drainTaskQueue вычитывает оставшиеся задачи из state.taskQueue и вызывает
// для каждой Task.Complete(ErrDispatcherStopped). Раз каждая задача достаётся
// ровно одному получателю (либо этому циклу, либо dispatch), состязание за
// конкретную задачу не приводит к двойному вызову Complete.
func (w *WorkerManager) drainTaskQueue(state *tenantState) int {
    dropped := 0
    for {
        select {
        case task := <-state.taskQueue:
            dropped++
            if task.Complete != nil {
                task.Complete(ErrDispatcherStopped)
            }
        default:
            return dropped
        }
    }
}
```

Покрыто тестом `TestRefreshTenantsRemoveTenantDrainsQueue` (`manager_test.go`), который эмпирически воспроизводит сценарий находки: тенант с `WorkerLimit: 1`, одна задача выполняется, две ждут в буфере, тенант удаляется — обе ожидающие задачи получают `Complete(ErrDispatcherStopped)`.

### 2. Логирование значения паники и ошибок без редактирования — потенциальная утечка чувствительных данных в логи ✅ исправлено (документация)

**Категория:** information-disclosure / logging · **Severity:** низкая (DREAD ≈ 3 — зависит целиком от того, что кладёт в `panic`/error пользовательская реализация `TaskExecutor`)

`runTask` логирует восстановленное значение паники и ошибку задачи без какой-либо фильтрации:

```go
// pool.go, runTask
p.logger.Error("task panic",
    slog.String("tenant_id", task.TenantID.String()),
    slog.String("task_id", task.TaskID.String()),
    slog.Any("panic", r),
    slog.String("stack", string(debug.Stack())))
```

`r` и `taskErr` происходят из пользовательского кода `Executor.Execute`, который пакет не контролирует. Если реализация паникует или возвращает ошибку, инкапсулирующую чувствительные данные (например, `panic(fmt.Sprintf("failed for card %s", cardNumber))`), это содержимое попадёт в структурированные логи в открытом виде на уровне Error.

Это не дефект самого пакета — библиотека обязана залогировать диагностику восстановления после паники, и не может знать, что "чувствительно" в непрозрачном значении `any`. Аналогичное поведение уже сознательно принято для трассировки стека (полезно для отладки, раскрывает только структуру кода, не данные). Устранение полностью средствами библиотеки невозможно без потери диагностической ценности.

**Исправление:** докстринг `TaskExecutor` (`manager.go`) дополнен явным предупреждением, что значение паники и возвращаемая ошибка логируются пулом целиком и без редактирования — реализации `Executor` не должны встраивать секреты/PII непосредственно в текст `panic()` или в возвращаемые ошибки, если логи пула могут быть доступны сторонам, для которых эти данные не предназначены. Код логирования не менялся — правка документационная, реализация уже была корректной (диагностика восстановления после паники обязана логироваться целиком).

### 3. `HealthStatus.Tenants[].TenantID` — потенциальное раскрытие идентификаторов тенантов через health-эндпоинт

**Категория:** information-disclosure · **Severity:** низкая (актуальна только для потребителей библиотеки, не для самого пакета — сетевого кода в пакете нет)

`Health()` возвращает `TenantID` (UUID) для каждого активного тенанта. Сам пакет не выполняет никакого сетевого взаимодействия, поэтому находка адресована потребителям: если `HealthStatus` транслируется напрямую во внешний, неаутентифицированный `/health`/`/ready` HTTP-эндпоинт, это позволяет перечислить UUID активных тенантов извне.

**Рекомендация:** отметить в докстринге `HealthStatus`/`Health()`, что при экспонировании через HTTP вызывающему коду следует либо аутентифицировать эндпоинт, либо агрегировать/убирать `TenantID` перед отдачей наружу.

## Без замечаний

Проверено и не выявило проблем:

- **`govulncheck ./...`** — 3 трассированные находки (GO-2026-5037, GO-2026-4602, GO-2026-4601), все — весьма вероятные ложные срабатывания консервативного анализа достижимости по графу вызовов через интерфейсы (например, `fmt.Sprintf`/`context.WithCancel` трассируются к несвязанным CVE в stdlib, которые в этом коде реально не достижимы). Рекомендация по гигиене независимо от этого: обновить toolchain Go выше `go1.26.0`, как только выйдет патч-версия.
- **`gosec -quiet ./...`** — единственная находка (G404, слабый ГПСЧ в `exponentialBackoff`, `pool.go:369`) уже корректно и адресно подавлена комментарием `//nolint:gosec` с обоснованием — использование не криптографическое (джиттер бэкоффа).
- **Инъекции** — grep-развёртка по всем production-файлам не выявила ни одного использования `exec.Command`, файлового/сетевого I/O, `database/sql`, шаблонизаторов, `unsafe`, TLS/криптографии, `os.Getenv`. Пакет — чистая in-memory библиотека конкурентности, классической поверхности инъекций не имеет.
- **`Task.ExecutorKey` → `ExecutorRegistry.Get`** — резолвинг ключа является поиском по map среди заранее зарегистрированных executor'ов (закрытый allow-list); даже полностью атакуемый `ExecutorKey` не даёт произвольного выполнения кода или выхода за пределы предварительно зарегистрированного набора.
- **Многотенантная модель "noisy neighbor"** — `Config.WorkerCount`/`Config.TaskQueueSize` намеренно общие для всех тенантов (задокументировано в самом коде), при этом конкурентность на тенанта отдельно ограничена `tenantState.sem`, размер которого берётся из `Tenant.WorkerLimit()`. Тенант с большим `WorkerLimit` (или совокупность многих тенантов) теоретически может забить общий `taskChan`, лишив пропускной способности других тенантов — архитектурный компромисс, а не дефект кода; `WorkerLimit` приходит из внутреннего `TenantProvider`, не напрямую от тенант-facing входа, поэтому реалистичная управляемость атакующим оценена как низкая.
- **Гонки данных** — `go test -race -count=1 ./...` чист; вся конкурентная работа с картами/срезами защищена соответствующими мьютексами/`sync.RWMutex`.
