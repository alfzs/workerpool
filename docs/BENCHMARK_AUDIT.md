# Аудит бенчмарков

Аудит по чек-листу `/cc-skills-golang:golang-benchmark`: в пакете не было
ни одной функции `Benchmark*` (подтверждено `grep` в раунде
`golang-modernize`, `docs/MODERNIZE_AUDIT.md`). Эта задача — не поиск
находки для исправления, а установка базового набора бенчмарков для горячих
путей пакета, с которым можно будет сравнивать будущие изменения через
`benchstat`.

## Выбор целей

- **`WorkerManager.SubmitTask`** — единственная точка входа задач в пакет,
  вызывается на каждой задаче в проде.
- **`ExecutorRegistry.Get`** — путь разрешения `Task.ExecutorKey` в
  `Task.Executor`, актуален для интеграций (например River), где executor
  передаётся по ключу, а не напрямую.
- **`WorkerManager.refreshTenants`** (steady-state, состав тенантов не
  меняется) — выполняется на каждом тике `TenantRefreshInterval` в течение
  всей жизни процесса; неизменный список тенантов — типичный случай.
  Параметризовано числом тенантов (1/10/100), так как `refreshTenants`
  выделяет новый `wantSet := make(map[uuid.UUID]struct{}, len(tenants))` на
  каждый вызов независимо от того, изменился ли состав.
- **`exponentialBackoff`** — чистая функция, вызывается на каждой неудачной
  попытке в `pool.executeWithRetry`.

## Дизайн-решение: `BenchmarkSubmitTask` и инвариант единственного читателя

Первая версия бенчмарка вызывала `SubmitTask` в плотном цикле `b.Loop()` без
ожидания завершения задачи. Это немедленно упиралось в
`ErrTenantQueueFull`: `SubmitTask` — это неблокирующая постановка в очередь
(fire-and-forget), а реальный диспетчер+пул (с OTel-спанами и переключением
горутин) на порядок медленнее одной операции отправки в канал, поэтому
очередь тенанта переполнялась быстрее, чем успевала разгружаться —
независимо от того, насколько большой была `TenantQueueSize` (испробовано
вплоть до 2 000 000 слотов — переполнение всё равно происходило при
`-benchtime=1s` по умолчанию).

Очевидный обходной путь — читать из `state.taskQueue` дополнительными
горутинами в обход штатного диспетчера — отклонён: `tenantState.taskQueue`
документирован как канал с ровно одним читателем на тенант (`manager.go`,
комментарий к `tenantState`, со ссылкой на `docs/CONCURRENCY_AUDIT.md`,
находка №1, где гонка между диспетчерами разных поколений уже была
причиной бага). Добавление читателя из теста нарушило бы этот инвариант.

Вместо этого `BenchmarkSubmitTask` измеряет **сквозную задержку одной
задачи** (`SubmitTask` → диспетчер → пул → `Complete`) через
`b.RunParallel`: каждая параллельная горутина ждёт `Complete` перед
следующей отправкой, поэтому в очереди никогда не оказывается больше
`GOMAXPROCS` задач одновременно — переполнение исключено структурно, а не
подбором размера очереди.

## Результаты (baseline)

```
goos: linux
goarch: amd64
cpu: Intel(R) Core(TM) i3-6300 CPU @ 3.80GHz

BenchmarkSubmitTask-4                             ~400000    ~2800 ns/op   1432 B/op   23 allocs/op
BenchmarkExecutorRegistryGet-4                    ~37000000    ~31 ns/op      0 B/op    0 allocs/op
BenchmarkRefreshTenantsSteadyState/tenants=1-4     ~7500000   ~164 ns/op      0 B/op    0 allocs/op
BenchmarkRefreshTenantsSteadyState/tenants=10-4     ~1050000  ~1040 ns/op    328 B/op    3 allocs/op
BenchmarkRefreshTenantsSteadyState/tenants=100-4     ~140000  ~8900 ns/op   2344 B/op    3 allocs/op
BenchmarkExponentialBackoff-4                     ~82000000    ~14 ns/op      0 B/op    0 allocs/op
```

(усреднено по `-count=10`, разброс между прогонами — единицы процентов;
полный вывод — `go test -bench=. -benchmem -count=10 -run=^$ .`)

## Выводы

- **`SubmitTask` сквозная задержка** (~2.8µs, 23 аллокации) в основном
  приходится на реальный пайплайн диспетчер→пул→OTel-спан, а не на саму
  `SubmitTask` — это ожидаемо для системы с трассировкой на каждую задачу и
  не является находкой.
- **`ExecutorRegistry.Get`** (~31ns, 0 аллокаций) и **`exponentialBackoff`**
  (~14ns, 0 аллокаций) — не в горячем пути с точки зрения оптимизации,
  оба на три порядка дешевле, чем стоимость самого выполнения задачи.
- **`refreshTenants` steady-state** масштабируется линейно по числу
  тенантов (~164ns → ~8.9µs при росте с 1 до 100), что соответствует
  выделению `wantSet` на каждый вызов независимо от изменений состава.
  При типичных `TenantRefreshInterval` (секунды-минуты в проде, не
  миллисекунды как в тестовом конфиге) и разумном числе тенантов эта
  стоимость пренебрежимо мала — фикс (например, пропуск пересборки `wantSet`,
  когда состав не изменился) не применён в этом раунде: нет свидетельств,
  что это реальное узкое место, а добавление ветки быстрого пути ради
  непроверенной гипотезы противоречило бы принципу «не оптимизировать без
  измерений». Эти числа фиксируются как baseline — если число тенантов или
  частота обновления вырастут настолько, что `refreshTenants` станет
  заметным в профиле продакшена, оптимизация может быть переоценена с
  `-cpuprofile` в руках.

Находок, требующих исправления кода, в этом раунде нет — весь раунд
задокументирован одним коммитом с добавлением `bench_test.go`.
