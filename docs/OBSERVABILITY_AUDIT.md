# Аудит наблюдаемости

Аудит по чек-листу `/cc-skills-golang:golang-observability`: пять сигналов
(логи, метрики, трейсы, профили, RUM) проверены по «Definition of Done»
чек-листа скилла применительно к библиотеке без собственного `main`/сетевого
входа (потребитель встраивает пакет в свой сервис и сам владеет
экспортом/дашбордами/алертами).

## Находки

### 1. Внутренние логи не используют `slog.*Context` — трассировочная корреляция терялась ✅ исправлено

**Категория:** log-trace-correlation · **Severity:** средняя — активные
OTel-спаны (`executeWithRetry`) существовали одновременно с логами по тем же
операциям, но ни один вызов `slog` не передавал `context.Context`, поэтому
`trace_id`/`span_id` не могли быть извлечены обработчиком логгера (например
`otelslog`-мостом, который чек-лист называет стандартным способом связывания
логов с трассировкой) — корреляция была невозможна даже при правильной
настройке потребителем.

```go
// pool.go, runTask — ДО
p.logger.Error("task panic",
    slog.String("tenant_id", task.TenantID.String()),
    ...)
```

```go
// pool.go, runTask — ПОСЛЕ
p.logger.ErrorContext(task.Ctx, "task panic",
    slog.String("tenant_id", task.TenantID.String()),
    ...)
```

**Исправление:** каждый вызов `slog` заменён на `*Context`-вариант с
наиболее специфичным доступным контекстом:

- `task.Ctx` — для логов, относящихся к конкретной задаче (`pool.go`:
  `runTask` — «task panic», «task failed with no completion handler»;
  `manager.go`: `dispatch` — «pool rejected task with no completion
  handler»).
- `w.ctx` (собственный контекст менеджера) — для логов уровня фонового
  обслуживания, не привязанных к конкретной задаче, но выполняющихся в
  рамках жизненного цикла менеджера (`manager.go`: `tenantRefresher` —
  «tenant refresh failed»; `refreshTenants` — «skipping tenant with nil id»,
  «invalid worker limit, using 1», «tenant removed, tasks dropped»).

**Оставлено без изменений (осознанно):** `pool.go`, `runWorker`/`stop`
(«worker panic», «pool stopped gracefully», «graceful timeout exceeded») и
`manager.go`, `Stop()` («stopping worker manager», «worker manager
stopped») — это события жизненного цикла компонента, а не конкретной
операции; единственный кандидат на контекст (`p.forceCtx`) относится к
дедлайну принудительной остановки, а не к «текущей операции», и его
использование для целей корреляции логов было бы вводящим в заблуждение.
Это то же разграничение, что и в `docs/DESIGN_PATTERNS_AUDIT.md` —
контекст пробрасывается там, где есть содержательная единица работы, а не
механически везде, где переменная лексически доступна.

Дополнительно обновлён пример в `doc.go` (godoc «Быстрый старт»): вызов
`Task.Complete` в примере тоже переведён на `slog.ErrorContext(ctx, ...)`,
и в раздел «Логирование и трассировка» добавлено явное описание конвенции
`*Context` + `otelslog`-мост, чтобы пример учил вызывающий код тому же
паттерну, который теперь последовательно применяется внутри пакета.

Регрессионный тест не добавлен: изменение затрагивает исключительно то,
какой `context.Context` передаётся в уже существующие вызовы `slog`
(наблюдаемый сайд-эффект — доступность значений контекста обработчику
логгера), а не бизнес-логику или её ветвление — юнит-тест не может
содержательно проверить «шёл ли конкретный `ctx.Value()` в logger.Handler»
без подмены самого `slog.Handler`, что для этого пакета было бы тестом
ради теста. Корректность проверена сборкой/vet/линтом/`-race`-прогоном
всего пакета (сигнатуры `slog.Logger.*Context` были бы отловлены
компилятором при ошибке типа).

## Проверено и не вызывает замечаний

- **`tenant.id` как атрибут метрики — cardinality-риск?** Рассмотрено и
  отклонено как находка. `pool.go`, `recordCompletion` добавляет
  `attribute.String("tenant.id", ...)` к `taskDuration` (histogram) и
  `tasksTotal` (counter) — чек-лист явно предупреждает про unbounded-label
  («NEVER use unbounded values... as label values»). Но архитектура пакета
  уже структурно ограничивает число тенантов: на каждого тенанта заведена
  постоянная горутина-диспетчер (`manager.go`, `dispatch`) плюс семафор —
  `ARCHITECTURE.md` приводит эталонный бюджет горутин из расчёта **200
  тенантов** (`WorkerCount=256` → 457 горутин итого). Библиотека физически
  не расcчитана на десятки/сотни тысяч одновременных тенантов (это исчерпало
  бы ресурсы планировщика горутин задолго до того, как cardinality метрик
  стала бы проблемой для бэкенда). При таком порядке величин (сотни
  тенантов × 2-3 статуса × ~10 бакетов гистограммы) итоговая cardinality —
  единицы тысяч серий, что не является «unbounded» в смысле чек-листа
  (сравнимо с обычным label по имени сервиса/окружению, а не с user ID или
  полным URL). Если потребитель библиотеки предполагает существенно большее
  число тенантов, чем предполагает эта архитектура, ограничение горутин уже
  станет узким местом раньше метрик — это не повод убирать `tenant.id` из
  метрик задним числом без запроса от реального использования.
- **Метрики объявлены** — `taskDuration` (`Float64Histogram`, латентность) и
  `tasksTotal` (`Int64Counter`, счётчик по статусу) в `pool.go`, `newPool`.
  Histogram, а не Summary — соответствует рекомендации чек-листа
  (агрегируемость на бэкенде, `histogram_quantile`). PromQL-комментарии над
  объявлениями метрик (конвенция чек-листа) не добавлены: у пакета нет
  собственного `/metrics`-эндпоинта или Prometheus-реестра — метрики
  экспортируются через глобальный `otel.GetMeterProvider()` потребителя,
  имя которого (`workerpool.task.duration`, `workerpool.tasks.total` —
  см. `pool.go`) уже подобрано так, чтобы быть узнаваемым при построении
  PromQL на стороне потребителя; конкретные пороги алертов и дашборды
  зависят от SLO конкретного развёртывания и не могут быть содержательно
  зафиксированы в коде библиотеки.
- **Спаны созданы на каждом значимом вызове** — `executeWithRetry`
  оборачивает каждый вызов `Executor.Execute` спаном с атрибутами
  `tenant.id`/`task.id`/`worker.id`/`attempt`; ошибки фиксируются через
  `span.RecordError()` (проверено чтением `pool.go` целиком). Дочерних
  вызовов к БД/внешним API внутри самого пакета нет — это ответственность
  реализации `TaskExecutor`, предоставляемой вызывающим кодом, и вне
  границ пакета.
- **Single handling rule (лог ИЛИ return, никогда оба)** — уже
  задокументирован явно в `manager.go` («Правило единственной обработки»,
  см. комментарий у `dispatch`) и соблюдается: `runTask`/`dispatch`
  логируют ошибку только в запасном канале (когда `Task.Complete` отсутствует
  или не задан), а не одновременно с передачей её через `Complete`.
- **PII в логах** — атрибуты логов и метрик ограничены `tenant_id`/`task_id`
  (UUID) и техническими полями (`limit`, `dropped`, `error`) — ни email,
  ни имена, ни содержимое задач не логируются. `task.Executor`/аргументы
  задачи, предоставляемые вызывающим кодом, не сериализуются пакетом нигде.
- **`HealthStatus`/`WorkerManager.Health()`** (`health.go`) — снимок
  saturation-сигнала (`PoolQueueDepth`/`Capacity`, `QueueDepth`/`Capacity`
  на тенанта, `TenantCount`) для liveness/readiness проб, уже содержит
  собственный документированный security-caveat со ссылкой на
  `docs/SECURITY_AUDIT.md` (находка №3: `TenantID` в снимке может
  перечислить тенантов, если эндпоинт неаутентифицирован) — покрытие
  «golden signal» saturation полное, замечаний нет.
- **Метрики + трейсы (exemplars)** — `recordCompletion` намеренно
  передаёт span-содержащий `ctx` (не `context.Background()`) в
  `p.taskDuration.Record`/`p.tasksTotal.Add` — уже реализовано ранее,
  подтверждено повторным чтением кода в этом раунде.
- **Профилирование (pprof/Pyroscope)** — не применимо. В репозитории нет
  `main`-пакета и HTTP-сервера (см. также `docs/MODERNIZE_AUDIT.md`,
  пункт про PGO) — переключение pprof через env-переменные и continuous
  profiling — забота процесса-хоста, который встраивает библиотеку, а не
  самого пакета.
- **RUM** — не применимо. Пакет — серверная библиотека без
  пользовательского интерфейса и без прямого взаимодействия с конечным
  пользователем; событий продуктовой аналитики (PostHog/Segment) здесь
  быть не может по определению домена.
- **Дашборды/алерты** — не применимо к самому коду пакета (владение
  Grafana/Prometheus-конфигурацией — на стороне потребителя), но метрики,
  необходимые для золотых сигналов (latency — `taskDuration`, errors —
  `tasksTotal` со статусом, saturation — `HealthStatus`), уже
  экспортируются пакетом — то есть все данные для построения алертов у
  потребителя есть, просто сами правила вне рамок библиотеки.
- **Уровни логирования** — `Debug` используется для событий частой,
  ожидаемой природы («tenant removed, tasks dropped» при рутинном
  обновлении состава тенантов), `Warn` — для деградации/восстановимых
  аномалий конфигурации (nil id, некорректный лимит, отклонённая пулом
  задача), `Error` — только для паник и невосстановимых сбоев. Разделение
  уровней уже было содержательным до этого раунда — только пробрасывание
  `ctx` было упущено.
