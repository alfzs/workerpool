## Проверено и не вызывает замечаний

### `govulncheck`: 3 «достижимых» уязвимости стандартной библиотеки — ложные срабатывания анализа графа вызовов

`govulncheck ./...` (при установленном `go1.26.0`) сообщил о 3
уязвимостях как «достижимых» через граф вызовов кода workerpool:

| ID | Пакет std | Исправлено в | Заявленная трасса |
| --- | --- | --- | --- |
| GO-2026-5037 | `crypto/x509` | go1.26.4 | `ExecutorRegistry.MustRegister` → `fmt.Sprintf` → `x509.HostnameError.Error` |
| GO-2026-4602 | `os` | go1.26.1 | `WorkerManager.Stop` → `context.WithCancel` → `os.ReadDir` |
| GO-2026-4601 | `net/url` | go1.26.1 | `WorkerManager.Stop` → `context.WithCancel` → `url.Parse` |

Проверка каждой трассы на реальном коде:

- `executor_registry.go:61` — `panic(fmt.Sprintf("workerpool: MustRegister %q: %v", key, err))`.
  `err` — обычный `error` (из `fmt.Errorf` в `Register`), не
  `x509.HostnameError`. `govulncheck` консервативно предполагает, что
  любое значение, переданное в `%v`, может динамически оказаться любым
  типом в программе, реализующим `error` — включая `x509.HostnameError`
  где-то в транзитивном графе — и помечает вызов как «достижимый», хотя
  в рантайме такого не происходит.
- `manager.go:200` — `w.cancel()` — это просто вызов замыкания,
  возвращённого `context.WithCancel(context.Background())` в
  `NewWorkerManager` (`manager.go:149`). Внутренняя реализация
  `context.WithCancel` не обращается ни к `os.ReadDir`, ни к
  `url.Parse` — трасса возникает из объединения узлов графа вызовов
  анализа `govulncheck` (одна и та же функция-хелпер `context` пакета
  используется во множестве мест транзитивных зависимостей, что даёт
  анализу неточную «достижимость» без учёта фактического потока данных).

Обе трассы — известное ограничение статического анализа `govulncheck`
на графах вызовов с интерфейсами/`any`-параметрами (over-approximation),
а не реальные пути исполнения. Пакетные и модульные срезы того же
отчёта (12 уязвимостей в импортируемых пакетах, 8 — в требуемых
модулях) `govulncheck` сам явно пометил как «код их не вызывает» — не
инструментальный шум, а прямое подтверждение того же вывода.

**Решение: код не менять.** Оговорка приведена для прозрачности отчёта
`govulncheck`, а не потому что уязвимость реальна.

## Проверка

- `gofmt -l .` — пусто.
- `go build ./...`, `go vet ./...` — чисто.
- `golangci-lint run ./...` — 0 issues.
- `go test ./... -race -count=1 -timeout 90s` — ok.
- `godig vulns <module>` — 0 результатов для каждой прямой и косвенной
  зависимости.
- `govulncheck ./...` — 3 «достижимых» находки в stdlib, разобраны выше
  и признаны ложными срабатываниями графа вызовов; 12+8 находок в
  зависимостях, отмеченных `govulncheck` как недостижимые.

## Итог

Находок, требующих изменения кода или `go.mod`, нет. Все зависимости
актуальны и без уязвимостей на момент проверки.
