# Аудит структуры проекта (project-layout)

Дата: 2026-07-06.

## Контекст

`workerpool` — библиотека (single-package, `package workerpool` в корне
модуля), без `cmd/`, без сервисной обвязки. Большая часть чек-листа
скилла (архитектура приложения, DI-подход, 12-factor) к библиотеке без
entrypoint'а не применима — она уже разобрана точечно в
`docs/DEPENDENCY_INJECTION_AUDIT.md` и `docs/DESIGN_PATTERNS_AUDIT.md`.
Ниже — то, что применимо: имя модуля, структура каталогов, служебные
файлы в корне.

## Находки

### 1. Отсутствует `Makefile`

**Серьёзность:** низкая (гигиена репозитория, не баг).

Скилл явно требует `Makefile` в корне любого Go-проекта для build
automation. В `workerpool` его нет — команды (`go test -race ./...`,
`gofmt -l .`, `go vet ./...`) задокументированы только текстом в
`CONTRIBUTING.md`, что означает их придётся копировать вручную и они
могут разойтись с тем, что реально гоняется в CI/локально.

**Исправление:** добавлен `Makefile` с целями, соответствующими
реальному составу репозитория (без `cmd/`, `bin/`, `run`, `install` —
их в скилловом шаблоне нет смысла копировать для чистой библиотеки):
`test`, `test-cover`, `benchmark`, `lint`, `lint-fix`, `fmt`, `vet`,
`audit` (govulncheck), `tidy`, `help`.

### 2. `.gitignore` не покрывает IDE- и тестовые артефакты

**Серьёзность:** низкая, но с наблюдаемым эффектом: `.idea/` весь этот
раунд аудитов висел как untracked в `git status`, потому что
`.gitignore` содержал только `/.claude/`.

**Исправление:** дополнен `.gitignore` стандартными паттернами
(`.idea/`, `.vscode/`, `*.test`, `coverage.out`, `coverage.html`,
`*.swp`, `.DS_Store`) по шаблону скилла, без специфичных для
сервисов записей (`bin/`, `dist/`, `.env*`, `tmp/` от `air`) —
у библиотеки без entrypoint'а и hot-reload им взяться неоткуда.

## Проверено и не вызывает замечаний

- **Имя модуля** — `github.com/alfzs/workerpool/v2`: строчными буквами,
  совпадает с репозиторием, суффикс `/v2` корректно отражает major
  версию по правилу совместимости импортов Go modules.
- **Плоская структура одного пакета** (`package workerpool` в корне,
  без `pkg/workerpool/` или `internal/`) — соответствует референсу
  скилла для однопакетных библиотек (ср. `google/uuid`): выносить
  единственный публичный пакет в поддиректорию с тем же именем, что и
  репозиторий, дало бы бессмысленный stutter
  (`workerpool/workerpool`). `internal/` не заведён — в кодовой базе
  сейчас нет приватной реализации, требующей сокрытия от внешних
  импортёров; заводить пустой `internal/` под будущее не требуется.
- **Отсутствие `cmd/`** — ожидаемо и корректно: это библиотека, не
  сервис/CLI; примеров-бинарников для демонстрации API нет, `example_test.go`
  (testable examples) для этого и предназначен.
- **`.golangci.yml`** — присутствует, конфигурация уже разобрана в
  прошлых аудитах (`docs/CODE_STYLE_AUDIT.md` и др.), явных пробелов
  не найдено повторно.
- **Тесты** — все `_test.go` совместно размещены с тестируемым кодом
  (`config_test.go`, `manager_test.go`, `executor_registry_test.go`,
  `bench_test.go`, `example_test.go`, `helpers_test.go`); `testdata/`
  не требуется — тесты не используют файловые фикстуры.
- **`go.work`** — не применимо: один модуль, не монорепозиторий.
- **Служебные файлы верхнего уровня** — `README.md`, `LICENSE`,
  `CHANGELOG.md`, `CONTRIBUTING.md` уже присутствуют (добавлены ранее,
  см. историю коммитов).

## Проверка

- `gofmt -l .` — пусто.
- `go build ./...`, `go vet ./...` — чисто.
- `golangci-lint run ./...` — 0 issues.
- `go test ./... -race -count=1 -timeout 90s` — ok.
- Новые цели `Makefile` (`make test`, `make lint`, `make fmt`, `make
  vet`) вручную прогнаны и дают тот же результат, что и прямые
  команды.
