# Аудит использования структур данных

Аудит по чек-листу `/cc-skills-golang:golang-data-structures`: преаллокация слайсов/map,
выбор array vs slice, `container/`-пакеты, `strings.Builder` vs `bytes.Buffer`,
generic-констрейнты, `unsafe.Pointer`/`weak.Pointer`, семантика копирования.

## Результат

Находок, требующих исправления, нет. Кодовая база уже последовательно следует
рекомендуемым практикам в тех местах, где это имеет значение.

## Проверено

- **Преаллокация слайсов** — везде, где размер известен заранее, `make` уже вызывается
  с ёмкостью: `health.go:72` (`make([]TenantHealth, 0, len(w.tenants))`),
  `manager.go:271` (`make([]uuid.UUID, 0, len(w.tenants))`),
  `executor_registry.go:84` (`make([]string, 0, len(r.executors))`). Единственные
  слайсы без преаллокации — накопление ошибок в `Config.Validate()`
  (`config.go`, до ~8 `append`) — вызывается один раз при старте, не hot path,
  преаллокация здесь не даёт измеримой выгоды.
- **Преаллокация map** — `wantSet := make(map[uuid.UUID]struct{}, len(tenants))`
  (`manager.go:323`) преаллоцирован корректно. `w.tenants` (`manager.go:154`) и
  `r.executors` (`executor_registry.go:24`) создаются без размера — на момент
  создания реальное количество тенантов/executor'ов ещё не известно (тенанты
  приходят позже через `TenantProvider.List`, executor'ы регистрируются по одному
  через `Register`), преаллокация невозможна и не является упущением.
- **Set-идиома** — `wantSet map[uuid.UUID]struct{}` в `refreshTenants` — ровно тот
  паттерн `map[T]struct{}`, который рекомендует чек-лист для множеств.
- **Array vs slice** — в пакете нет данных фиксированного размера, известного на
  этапе компиляции (хэшей, IP-адресов, матриц) — использование слайсов везде,
  где они есть, оправдано.
- **`uuid.UUID` как ключ map** — это `[16]byte`, сравнимый тип, корректно
  используется как ключ (`w.tenants`) без обёрток.
- **`container/list`, `container/heap`, `container/ring`** — не используются;
  не является находкой. В пакете нет очередей с произвольной вставкой в середину,
  приоритетных очередей или кольцевых буферов — вся буферизация задач уже
  реализована через каналы (`chan Task`), что для FIFO-очереди с фиксированной
  ёмкостью эквивалентно `container/ring` по семантике, но с встроенной
  поддержкой блокировки/`select`, недоступной у `container/ring`.
- **`strings.Builder` / `bytes.Buffer`** — в пакете нет накопления строк в цикле;
  единственное форматирование строк — разовые `fmt.Sprintf`/`fmt.Errorf` для
  сообщений об ошибках, не требующие `Builder`.
- **`slices`/`maps` (Go 1.21+)** — в пакете нет ручных циклов поиска/сортировки,
  которые стоило бы заменить на `slices.Contains`/`slices.Sort` — все существующие
  `for range` — это построение снимков состояния, а не поиск.
- **Generic-коллекции** — в пакете нет собственных generic-контейнеров; вводить
  их не требуется, так как единственные коллекции (`map[uuid.UUID]*tenantState`,
  `map[string]TaskExecutor`) уже строго типизированы конкретными доменными типами.
- **Копирование структур** — `Task` (88 байт) намеренно передаётся по значению
  через каналы (см. `//nolint:containedctx` на `Task.Ctx` и докстринг типа) — это
  осознанный выбор в пользу локальности кэша: буфер `chan Task` — непрерывный
  массив значений, без косвенности через указатель и дополнительной аллокации на
  задачу, в отличие от `chan *Task`. `Config` (только скалярные поля и
  вложенный `RetryPolicy`, тоже только скаляры) хранится по значению в `pool` и
  `WorkerManager` — копируется один раз при создании, дальше только читается,
  не является поводом для перехода на указатель. Карты с указателями на большие
  значения (`map[uuid.UUID]*tenantState`) уже используют `*tenantState`, а не
  `tenantState` по значению — не копируют состояние тенанта при каждом доступе
  к map.
- **`unsafe.Pointer` / `weak.Pointer`** — не используются; не является находкой.
  В пакете нет FFI, ручной работы с layout памяти, кэшей или canonicalization-map,
  которым требовались бы слабые ссылки — `ExecutorRegistry` не является кэшем
  с вытеснением, это постоянный реестр на весь жизненный цикл приложения.
