# Аудит внедрения зависимостей (DI)

Аудит по чек-листу `/cc-skills-golang:golang-dependency-injection` в режиме Refactor mode:
глобальные переменные/`init()` для сервисов, конкретные типы вместо интерфейсов
там, где они потребляются, паттерн service-locator (передача контейнера как
зависимости).

Пакет — небольшая библиотека из трёх взаимодействующих компонентов
(`WorkerManager`, `pool`, `ExecutorRegistry`) с неглубоким графом зависимостей.
Согласно таблице решений чек-листа (< 10 сервисов → ручной DI без библиотеки),
использование ручного конструкторного внедрения через `WorkerManagerParams`
уже является правильным выбором — вопрос только в его последовательности.

## Находки

### 1. `slog.Default()` — скрытая зависимость от глобального изменяемого состояния вместо инжектируемого логгера ✅ исправлено

**Категория:** hidden-dependency / global-state · **Severity:** низкая-средняя —
не влияет на корректность выполнения, но нарушает тестируемость и изоляцию
инстансов: до фикса ни `WorkerManager`, ни `pool` не принимали логгер как
параметр, а оба независимо обращались к глобальному `slog.Default()`:

```go
// manager.go, NewWorkerManager
return &WorkerManager{
    logger: slog.Default().With(slog.String("component", "worker_manager")),
    ...
}

// pool.go, newPool
return &pool{
    logger: slog.Default().With(slog.String("component", "pool")),
    ...
}
```

Это ровно паттерн, который чек-лист приводит как канонический плохой пример
(`NewUserService()`, скрыто читающий `os.Getenv` вместо принятия зависимости
через конструктор): вызывающий код не может передать нужный логгер явно —
единственный способ повлиять на логирование до создания `WorkerManager` —
мутировать процесс-глобальное состояние через `slog.SetDefault()` до вызова
`NewWorkerManager`, что и было явно задокументировано как обязательный шаг
(«настройте глобальный логгер до вызова этой функции»). Последствия:

- Два независимых `WorkerManager` в одном процессе не могут иметь разные логгеры.
- Тесты, которым нужно проверить содержимое лога (например, что
  `refreshTenants` действительно логирует ошибку через `w.logger.Error(...)`),
  вынуждены были бы мутировать глобальный `slog.Default()`, что не сочетается
  с `t.Parallel()` (уже используемым практически во всех тестах пакета).
- `pool` и `WorkerManager` независимо обращались к `slog.Default()` дважды —
  если бы вызывающий код заменил глобальный логгер между двумя вызовами
  (маловероятно, но не исключено конфигурацией), компоненты получили бы
  рассинхронизированные логгеры.

**Исправление:** добавлено опциональное поле `WorkerManagerParams.Logger
*slog.Logger`. `NewWorkerManager` резолвит его в начале (`slog.Default()`,
если не задан) и передаёт **один и тот же** экземпляр как в `WorkerManager`,
так и в `poolParams.logger` — оба компонента добавляют свой атрибут
`component` поверх одного инжектированного логгера, а не создают независимые
обращения к глобальному состоянию:

```go
logger := p.Logger
if logger == nil {
    logger = slog.Default()
}

pl, err := newPool(poolParams{config: p.Config, logger: logger})
...
return &WorkerManager{
    logger: logger.With(slog.String("component", "worker_manager")),
    ...
}
```

Обратная совместимость сохранена: `Logger` — опциональное поле, поведение по
умолчанию (`slog.Default()`) не изменилось для существующих вызывающих, не
задающих его явно.

## Проверено и не вызывает замечаний

- **Отсутствие глобальных переменных / `init()` для сервисов** — в пакете нет
  ни одной package-level `var`, хранящей сервис или зависимость (единственные
  package-level `var`-блоки — объявления сентинел-ошибок в `errors.go`, что не
  является DI-нарушением), и нет ни одной функции `init()`.
- **Интерфейсы определены на стороне потребителя** — `TenantProvider`,
  `Tenant`, `TaskExecutor` объявлены в `manager.go`, там же, где они
  используются (`WorkerManager`, `pool`), а не в гипотетическом пакете
  конкретной реализации (например, River-интеграции) — соответствует принципу
  «accept interfaces, return structs».
- **`ExecutorRegistry` — не service locator** — несмотря на внешнее сходство
  (реестр, разрешающий строковый ключ в реализацию во время выполнения), это
  не анти-паттерн: причина существования реестра — потребность сериализовать
  ссылку на исполнителя в персистентном job store (River/Postgres), где нельзя
  сохранить сам интерфейс `TaskExecutor`. Реестр передаётся явно как поле
  `WorkerManagerParams.ExecutorRegistry`, а не читается из глобальной
  переменной и не передаётся дальше как контейнер — сам `WorkerManager`
  использует из него только точечный `Get(key)` в `SubmitTask`, а не
  прокидывает реестр целиком в нижестоящий код.
- **OTel `otel.GetTracerProvider()` / `otel.GetMeterProvider()`** — формально
  похоже на находку №1 (обращение к глобальному состоянию внутри `newPool`),
  но не поднимается как находка: это задокументированная, официально
  рекомендуемая экосистемой OpenTelemetry Go практика для библиотек — принимать
  провайдеры через глобальные `otel.Get*Provider()` (которые возвращают
  no-op-реализацию по умолчанию и становятся полезными после того, как
  приложение один раз настроит их через `otel.SetTracerProvider`/`SetMeterProvider`),
  а не требовать их явной передачи через каждый конструктор. В отличие от
  `slog.Default()`, у OTel это единственный поддерживаемый экосистемой паттерн
  для библиотек, а не результат недосмотра.
- **Контейнер как зависимость (service-locator anti-pattern)** — в пакете нет
  DI-контейнера вообще; единственная точка сборки — параметры конструктора
  (`WorkerManagerParams`), не хранящиеся и не передающиеся дальше как единое
  целое — `pool` получает только нужные ему поля (`config`, `logger`) через
  `poolParams`, а не весь `WorkerManagerParams`.
- **Глубина графа зависимостей** — `WorkerManager → pool`, `WorkerManager →
  ExecutorRegistry` (опционально), `WorkerManager → TenantProvider`
  (интерфейс) — максимум один уровень косвенности, соответствует рекомендации
  «keep the dependency graph shallow».
- **Мокирование на границе интерфейса** — существующие тестовые моки
  (`mockTenantProvider`, `mockExecutor`, `mockTenant` в `helpers_test.go`)
  уже подтверждают, что все внешние зависимости внедряются через интерфейсы и
  тривиально подменяются в тестах — DI уже работает как задумано для всех
  зависимостей, кроме находки №1.
