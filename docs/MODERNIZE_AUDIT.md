# Аудит модернизации

Аудит по чек-листу `/cc-skills-golang:golang-modernize` в Full-scan mode:
устаревшие пакеты, языковые фичи (range-over-int, min/max, any, итераторы),
апгрейды стандартной библиотеки (`slices`, `maps`, `cmp`, `slog`), тестовые
паттерны (`t.Context`, `b.Loop`, `synctest`), тулинг (`golangci-lint` v2,
`govulncheck`).

## Контекст

- `go.mod`: `go 1.26.0` — уже последняя стабильная версия, апгрейд не требуется.
- `.golangci.yml` уже включает линтер `modernize` (доступен с golangci-lint
  v2.6.0; здесь используется v2.12.2) — `golangci-lint run --enable-only
  modernize ./...` → **0 issues** до находки ниже (линтер не поймал её, так
  как `cmp.Or` — это предпочтение стиля, а не строго устаревший паттерн).
- `.modernize` в корне проекта отсутствует — ранее проигнорированных
  предложений нет.

## Находки

### 1. Ручной nil-default вместо `cmp.Or` ✅ исправлено

**Категория:** stdlib-upgrade (Go 1.22+) · **Severity:** низкая (только
читаемость, поведение не менялось).

```go
// manager.go, NewWorkerManager — ДО
logger := p.Logger
if logger == nil {
    logger = slog.Default()
}
```

`*slog.Logger` — comparable-тип с нулевым значением `nil`, что ровно
подходит под сигнатуру `cmp.Or[T comparable](vals ...T) T` (возвращает
первый аргумент, не равный нулевому значению типа):

```go
// manager.go, NewWorkerManager — ПОСЛЕ
logger := cmp.Or(p.Logger, slog.Default())
```

Учтено, что `cmp.Or` вычисляет **все** аргументы заранее (не ленивое
вычисление, в отличие от `||`/тернарного оператора в других языках) — здесь
это безопасно, так как `slog.Default()` — дешёвый геттер пакетной
переменной, не имеющий побочных эффектов, и вызывается меньше одного раза за
жизненный цикл процесса (только при создании `WorkerManager`), так что
двойное вычисление не является проблемой производительности.

## Проверено и не вызывает замечаний

- **Устаревшие пакеты** (`math/rand`→`v2`, `crypto/elliptic`→`ecdh`,
  `reflect.SliceHeader`→`unsafe.Slice`, `runtime.SetFinalizer`→`AddCleanup`
  и т.д.) — ни один не используется в пакете; `grep` по каждому из списка
  чек-листа не дал совпадений.
- **`interface{}` вместо `any`** — не используется нигде в пакете
  (`grep interface{}` — пусто); весь код уже пишет `any` там, где нужен
  универсальный тип.
- **`range` по int вместо C-style цикла** — уже используется везде, где
  применимо (например, `for range 2000` в `TestSubmitTaskNoRaceWithTenantRemoval`,
  добавленном в раунде `golang-concurrency`); классических
  `for i := 0; i < n; i++` в непортированном виде не найдено.
- **`sort.Slice`** — не используется; сортировки в пакете нет вообще (только
  построение снимков `[]uuid.UUID`/`[]string` без упорядочивания —
  зафиксировано также в `docs/DATA_STRUCTURES_AUDIT.md`).
- **`sync.OnceFunc`/`OnceValue`** — в пакете нет паттерна ленивой
  однократной инициализации, который стоило бы заменить (единственная
  «глобальная» инициализация — `slog.Default()`, разрешаемая один раз в
  конструкторе, а не через `sync.Once`).
- **`sync.WaitGroup.Go`** (Go 1.25+) — уже применяется в
  `TestSubmitTaskNoRaceWithTenantRemoval` (добавлен в раунде
  `golang-concurrency`); других мест с ручным `Add`/`go func(){ defer Done()
  }()`, подходящих под замену, не найдено — `pool.go`/`manager.go`
  используют `errgroup`/семафоры там, где нужна отмена по ошибке или лимит
  конкурентности, что `wg.Go` не заменяет.
- **`t.Context()` (Go 1.24+)** — все использования `context.Background()` в
  тестах намеренные и не являются кандидатами: это `Task.Ctx` — контекст,
  моделирующий контекст *вызывающего* кода задачи, а не контекст самого
  теста, поэтому привязка к жизненному циклу `t.Context()` (отменяется по
  завершении теста) изменила бы семантику тестов (`TestContextCancellationPropagated`,
  `TestExecuteRespectsConfiguredTaskTimeout` — оба управляют временем жизни
  контекста задачи вручную через `cancel()`/таймаут). В `example_test.go`
  `context.Background()` используется внутри `Example*`-функций, у которых
  нет `*testing.T` вовсе — `t.Context()` там физически недоступен.
- **`b.Loop()` (Go 1.24+)** — в пакете нет ни одного `Benchmark*` — нечего
  модернизировать.
- **`testing/synctest`** — не применимо: конкурентные тесты пакета уже
  используют реальные таймауты и `-race` (см. `docs/CONCURRENCY_AUDIT.md`),
  а не искусственное время, для которого `synctest` был бы полезен.
- **Итераторы (`iter.Seq`, `range-over-func`, Go 1.23+)** — в пакете нет
  собственных генераторов последовательностей и нет мест, где итератор
  упростил бы код (см. также `docs/DATA_STRUCTURES_AUDIT.md`, раздел про
  потоковую обработку — не применимо к домену пакета).
- **`strings.SplitSeq` и итераторные варианты (Go 1.24+)** — `strings.Split`
  не используется вовсе.
- **`go.mod` tool-директивы (Go 1.24+)** — в `go.mod` нет `tool`-зависимостей
  для миграции; `golangci-lint`/`govulncheck` устанавливаются вне модуля.
- **PGO** — вне рамок аудита библиотеки (в этом репозитории нет `main`-пакета
  с производственной нагрузкой, для которой имело бы смысл собирать профиль).
- **`golangci-lint` v2 + `modernize`** — уже настроено и включено
  (`golangci-lint --version` → 2.12.2, `.golangci.yml` содержит `modernize`
  в списке включённых линтеров) — апгрейд не требуется.
- **`govulncheck`** — не установлен как часть этого прохода; отдельная
  проверка уязвимостей зависимостей не входит в чек-лист `golang-modernize`
  дословно, но упомянута как high-priority пункт — `go list -m -u all`
  показывает единственную зависимость с доступным апгрейдом:
  `github.com/rogpeppe/go-internal` (`v1.14.1` → `v1.15.0`), транзитивная
  тестовая зависимость (через `testify`), не импортируемая напрямую кодом
  пакета — рутинный бамп версии, не являющийся модернизацией устаревшего
  API, поэтому не применён в рамках этого прохода.
- **`encoding/json/v2`** — пакет не использует `encoding/json` вовсе (нет
  сериализации в JSON) — не применимо.
