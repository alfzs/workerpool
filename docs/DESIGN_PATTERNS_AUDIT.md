# Аудит паттернов проектирования

Аудит по чек-листу `/cc-skills-golang:golang-design-patterns` в Review mode:
`init()`-злоупотребления, неограниченные ресурсы, отсутствующие таймауты,
неявное глобальное состояние, конструкторы, panic-дисциплина, `defer Close()`,
regexp/enum-идиомы.

## Находки

### 1. `Config.TaskTimeout` документирован, но никогда не применяется ✅ исправлено

**Категория:** missing-timeout · **Severity:** высокая — задокументированный
публичный контракт полностью не реализован, что может привести к
незавершающимся задачам в проде.

`Config.TaskTimeout` заявлен в трёх местах как дедлайн по умолчанию для
одного выполнения задачи:

```go
// config.go
// TaskTimeout — дедлайн по умолчанию для одного выполнения задачи.
// Вызывающий код может задать более жёсткий дедлайн через Task.Ctx.
// Должно быть > 0.
TaskTimeout time.Duration `yaml:"task_timeout" env-default:"5m"`
```

```markdown
<!-- ARCHITECTURE.md -->
| `TaskTimeout` | 5m | Дедлайн задачи по умолчанию |
```

Значение валидируется при старте (`Config.Validate()` требует `> 0`), но
нигде в пути выполнения задачи не читается. `pool.executeWithRetry` строил
контекст задачи так:

```go
// pool.go, executeWithRetry — ДО исправления
taskCtx, taskCancel := context.WithCancel(task.Ctx)
defer taskCancel()
```

`context.WithCancel` не добавляет дедлайн — если `Task.Ctx`, переданный
вызывающим кодом, сам не несёт дедлайна (например, `context.Background()`,
что и показано в примере быстрого старта в `doc.go` до текущего фикса — там
`ctx` формируется вызывающим кодом вручную через `context.WithTimeout`,
но сама библиотека не гарантирует это для произвольного вызывающего кода),
`Executor.Execute` может выполняться неограниченно долго вопреки
задокументированному контракту «дедлайн по умолчанию». Единственная защита
от зависшей задачи в этом случае — `GracefulTimeout` при `Stop()`, который
не помогает, если менеджер продолжает работать в штатном режиме.

**Исправление:** дедлайн берётся из конфигурации через `context.WithTimeout`:

```go
// pool.go, executeWithRetry — ПОСЛЕ исправления
taskCtx, taskCancel := context.WithTimeout(task.Ctx, p.config.TaskTimeout)
defer taskCancel()
```

Семантика «вызывающий код может задать более жёсткий дедлайн через
Task.Ctx» сохраняется автоматически: `context.WithTimeout` берёт более
раннюю из двух границ — если `task.Ctx` уже несёт более ранний дедлайн, чем
`p.config.TaskTimeout`, побеждает он; если дедлайна нет вовсе (как в
`context.Background()`), применяется `TaskTimeout`.

**Регрессионный тест** — `TestExecuteRespectsConfiguredTaskTimeout`
(`manager_test.go`) — отправляет задачу с `Task.Ctx: context.Background()`
(намеренно без собственного дедлайна) и коротким `Config.TaskTimeout = 50ms`,
проверяет, что `Complete` вызывается с `context.DeadlineExceeded` в течение
5 секунд. До исправления тест воспроизводимо зависал бы до собственного
таймаута теста (5 секунд ожидания `<-done`, никогда не срабатывающего).

## Проверено и не вызывает замечаний

- **`init()` / глобальные переменные для сервисов** — уже проверено в
  `docs/DEPENDENCY_INJECTION_AUDIT.md` (находка №1 про `slog.Default()` там
  же и исправлена) — других `init()`/глобальных сервисов нет.
- **Функциональные опции vs параметр-структура** — конструкторы пакета
  (`NewWorkerManager(WorkerManagerParams{...})`, `NewExecutorRegistry()`)
  используют паттерн «параметр-структура», а не функциональные опции,
  которые чек-лист называет предпочтительными. Это не поднимается как
  находка: `WorkerManagerParams` — не публичный API с историей эволюции,
  требующей обратной совместимости через `With*`-опции, а составление одной
  структуры целиком на старте приложения (единственная точка вызова
  `NewWorkerManager` за жизненный цикл процесса) — ровно тот случай, где
  чек-лист допускает builder/параметр-структуру: усложнение до
  функциональных опций добавило бы код без выгоды, так как поля не имеют
  комбинаторной валидации между собой (кроме уже реализованной в
  `Config.Validate()`).
- **Enums должны начинаться с 1** — в пакете нет ни одного `iota`-перечисления
  (`grep iota` — пусто); нечего проверять.
- **Panic — только для багов** — единственный `panic()` вне тестов —
  `ExecutorRegistry.MustRegister`, ровно тот случай, который чек-лист называет
  допустимым («Must* constructors used at init time»): паника происходит один
  раз при регистрации executor'ов на старте приложения (дублирующийся ключ —
  программная ошибка конфигурации, а не runtime-ошибка вызывающего кода).
  Обычный путь регистрации, `Register`, возвращает `error`.
- **`defer Close()` сразу после открытия ресурса** — в пакете нет
  `os.Open`/`sql.Open`/аналогичных ресурсов, требующих `Close()` — вся
  ресурсная модель построена на каналах и контекстах, управляемых через
  `Stop()`/graceful shutdown, что уже отдельно проверено в
  `docs/CONCURRENCY_AUDIT.md`.
- **`runtime.AddCleanup` / `runtime.SetFinalizer`** — не используются; не
  является находкой, так как в пакете нет типов, оборачивающих внешние
  ресурсы (файловые дескрипторы, cgo-хендлы), которым требовалась бы
  финализация при потере ссылки.
- **Ограничение ресурсов (pool sizes, queue depths)** — `WorkerCount`,
  `TaskQueueSize`, `TenantQueueSize` — все размеры каналов и пулов заданы
  через `Config` и валидируются (`> 0`) в `Config.Validate()`; неограниченных
  очередей или пулов в пакете нет.
- **Retry проверяет отмену контекста между попытками** — уже подтверждено в
  `docs/CONCURRENCY_AUDIT.md`: `executeWithRetry` использует `select` на
  `taskCtx.Done()` между попытками, а не безусловный `time.Sleep`.
- **`strings.Builder` в циклах** — уже подтверждено в
  `docs/DATA_STRUCTURES_AUDIT.md`: накопления строк в цикле в пакете нет.
- **string vs []byte** — в пакете нет горячих путей с преобразованием между
  `string` и `[]byte` (нет сериализации/парсинга бинарных данных); единственные
  строки — ключи реестра executor'ов и сообщения об ошибках, что не требует
  `[]byte`.
- **Итераторы/потоковая обработка больших данных** — не применимо: пакет не
  читает большие наборы данных из БД/HTTP (это забота `TenantProvider` и
  `TaskExecutor`, реализуемых вызывающим кодом).
- **`//go:embed` для статических ассетов** — в пакете нет статических файлов
  для встраивания.
- **`crypto/rand` для ключей/токенов** — единственное использование
  случайности — `math/rand`-джиттер в `exponentialBackoff`, явно помеченный
  `//nolint:gosec` с обоснованием (не криптографический контекст) — уже
  проверено ранее (аудит безопасности), не является находкой для этого
  чек-листа.
- **Regexp, скомпилированный один раз на уровне пакета** — в пакете вообще
  нет использования `regexp` — нечего проверять.
- **Compile-time interface checks** — уже присутствуют:
  `var _ Tenant = (*mockTenant)(nil)`, `var _ TenantProvider =
  (*mockTenantProvider)(nil)`, `var _ TaskExecutor = (*mockExecutor)(nil)`
  (`helpers_test.go`), плюс аналоги в `example_test.go` — соответствует
  чек-листу (проверено также в `docs/STRUCTS_INTERFACES_AUDIT.md`, если
  применимо).
- **Минимизация зависимостей** — `go.mod` содержит всего 5 прямых
  зависимостей (`google/uuid`, три пакета `go.opentelemetry.io/otel/*`,
  `golang.org/x/sync`) — все обоснованы функциональностью пакета (UUID
  тенантов/задач, трассировка/метрики, `errgroup`-подобные примитивы), лишних
  тяжёлых зависимостей нет.
- **Design for testability** — уже подтверждено в
  `docs/DEPENDENCY_INJECTION_AUDIT.md`: все внешние зависимости принимаются
  через интерфейсы, существующие моки демонстрируют тривиальную
  подменяемость.
